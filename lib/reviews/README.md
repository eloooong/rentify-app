# Two-sided review contract

Person B owns these RPCs/APIs; Person A owns review screens and rating displays. PR #56 is merged and the hosted test backend is ready for UI integration. Angel selected immediate publication on 5 November 2026; see [policy](../../DECISIONS.md#9-reviews-for-the-demo).

Each verified, active participant with a profile may submit one review of the other participant after the booking is `completed`. No other booking status qualifies. A calendar date, payment, handover or return alone does not prove completion. This feature adds no completion/settlement transition; B3.3 remains required for real completed bookings. An inactive counterparty does not remove the author's right to review a completed rental.

A rating is an integer 1–5. Optional plain-text `comment` defaults to `""`, is trimmed of surrounding ASCII spaces and contains at most 2,000 Unicode characters; NUL is rejected. Reviews publish immediately, have no submission deadline and cannot be edited/deleted by ordinary users. Submit only content suitable for public display; do not include contact details or payment information. Render comments as text, never raw HTML. Reporting/moderation remains B3.4. Reviews remain public if a participant later becomes suspended or a listing is paused/deleted.

| Endpoint                        | Input                                                                    | Result                                                                     |
| ------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| `GET /api/bookings/:id/review`  | Verified participant session, no query                                   | `{booking_id,can_review,reason,review}`                                    |
| `POST /api/bookings/:id/review` | Strict `{rating:number,comment?:string}`                                 | `201 {data:Review,replayed:false}`; exact retry `200` with `replayed:true` |
| `GET /api/profiles/:id/reviews` | Public; `page=1..10000`, `pageSize=1..50`, optional `role=owner\|renter` | `{data:Review[],pagination:{page,pageSize,total},summary:{count,average}}` |

`Review={id,author_id,subject_id,author_name,subject_role:'owner'|'renter',rating,comment,created_at}`. IDs are UUIDs and timestamps include a UTC offset. Booking IDs, rental dates, email/phone, account roles/statuses and payment details are absent from public DTOs. `subject_role` is the reviewed person's role in that booking: a renter reviews an owner, and an owner reviews a renter. Profile summaries follow the same optional role filter as the rows; average is rounded to two decimals and is null for no reviews. Public unknown profile IDs return an empty page. Lists sort by creation timestamp and UUID descending; refresh page one after changes because offset pages are not frozen snapshots.

Private eligibility `reason` is null when allowed, otherwise `already_reviewed`, `booking_incomplete` or `account_inactive`. An existing review remains readable to its author after suspension. An exact retry replays the stored rating/comment without creating another row or audit; changed rating/comment returns `409 review_exists`. Both participants can submit independently and concurrent identical submissions produce one review. Author, subject and booking identities are server-derived; caller-supplied identity/publication fields are rejected.

Private routes use verified session cookies; mutations also require the canonical Origin and application/json. Missing/outsider bookings return 404 (including an admin outside the booking). Public reads require no account. Responses use private/no-store JSON, including public review reads, to avoid serving mixed session responses from cache. Error shape remains `{error:{code,message,fields?}}`: 401 `sign_in`, 403 `forbidden`/`origin`, 404 `not_found`, 409 `review_not_allowed`/`review_exists`/`retry`, 400 `validation`/invalid JSON, 413 oversized body, 415 content type, 503 unavailable. Unknown/repeated query parameters and unknown JSON fields are rejected.

Database commands repeat identity/eligibility/input checks: `submit_booking_review(p_booking,p_rating,p_comment default '')`, `get_booking_review(p_booking)` and `list_profile_reviews(p_subject,p_role default null,p_page default 1,p_page_size default 20)`. Reviews retain deny-all RLS and no direct anon/authenticated table grants; the server service role has SELECT only. Writes go through the authenticated command; public reads go through the narrow projection RPC. The public projection includes only reviews whose stored author/subject match a genuinely completed booking, including pre-existing records. Internal helpers and privileged writes are not exposed to clients.

Verification uses `npm run db:test:reviews` for real Auth/RPC/concurrent submissions, `npm run test:reviews:http` with a production app on localhost:3000, and `npm run db:test` for grants/helper checks. HTTP tests accept the existing local-only `RENTIFY_TEST_BASE_URL` override when the app's canonical Origin matches. Isolated test fixtures set completed status through trusted local SQL explicitly; they do not pretend the unfinished B3.3 lifecycle exists. No hosted migration is applied before implementation review/merge.
